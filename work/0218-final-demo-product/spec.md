# Final-demo product behavior

1. Management uses the existing authenticated BFF. Trusted team comes only from authenticated principal. Tenant metadata is display-only, owner/admin writable and audited; project grants use existing per-project operations, not destructive role replacement.
2. Setup gains optional additive submission-project, observability and organization display fields. Old consumers remain compatible. New clients distinguish inspection projects from server-confirmed submission projects; unsupported lists fall back to existing admission-rule suggestions, never grant authority.
3. One in-memory form draft has a stable canonical request after first submission. Network/unreadable/server failures retain that draft and reconcile via the evidence endpoint. A definite non-acceptance can be corrected with a fresh logical request. No task body or token is persisted in browser storage. A session-scoped reference alone may restore an uncertain query.
4. Setup can be loaded with explicit project/template context. Context changes abort/ignore obsolete responses and reset dependent permissions. task.type is a user-selected supported existing task type; task.input is canonical objective/workName plus optional repository fields. No schema change or authority from task text.
5. Policy management supports safe reading of project-owned versions and optional expected active identity. Under the existing project advisory lock, compare active identity before immutable insert/activation and audit commit. Legacy apply without precondition retains documented behavior. History uses immutable version documents and structured activation audit rows committed atomically, not slash-prefix matching on legacy audit strings or a second Work evidence store. Pre-upgrade activation history is not fabricated.
6. Work comparison consumes only authorized API evidence views. Duplicate strips all issued state/credentials and revalidates registered template. Immutable historical policy is addressed explicitly by project/id/version; missing means unavailable, never today's policy.
7. Telemetry configuration is reported from resolved Platform adapters. Configured does not imply exporting or downstream ingestion. Diagnostic destinations are operator-supplied safe HTTPS or local loopback HTTP (or existing same-origin authenticated proxy) with no URL userinfo or token parameters; no client-side SSRF fetch.
8. Safety summaries distinguish admission denial, governed call denial, execution failure and unknown network failure. Native enforcement verification requires independently captured positive/negative controls; runtime NetworkActive alone is configured evidence, not proof of blocking.
9. Local acceptance service is loopback-bound and explicitly labelled synthetic identities/reference execution. It exercises actual Go admission/evidence and disposable PostgreSQL management; browser tests separately cover actual UI behavior. Never selectable as a production authentication fallback.
10. Catalog discovery is permission-filtered server-side and independent of Work submission. Directory entries bind project and template identity. Viewers may prepare a visible template request, but submission is reauthorized; Owner does not bypass claim Policy. Installation details are operator-only, with explicit safe projections rather than arbitrary adapter config.
11. Researcher is registered only to research, never the global fallback. Same principal/project/template/Policy supports public-source and synthetic customer-retention tasks requesting different tool scopes. Existing engineer/incident-reader and payments/billing remain intact.
12. The existing Go MCP service retains read_file and adds fixed-source web_fetch and read-only crm_read. Inputs are allowlisted IDs, not arbitrary URLs/SQL. Public HTTP requests use strict HTTPS, public-IP validation at dial time, no redirects/proxies/cookies/custom headers, deadlines and size bounds. Fixture CRM data is read from a trusted read-only dataset root, never mounted into an Agent. Gateway authorization and server receipts are independently tested.
13. Owner clarified the desired public-network demo requires no API key: web.read(url) reads a supplied public HTTPS page, not keyword search. Explicit bounded text parameter mode transports the URL; legacy profiles remain allowlisted by default, unknown/mixed modes fail closed. Worker grammar and host validation retain route/scope and byte bounds. MCP validates URL/DNS/IP at the actual dial, refuses private/metadata/loopback targets, redirects, credentials, proxies and oversized/non-text responses. Only trusted MCP accesses the page; no Agent Pod network grant. Local deterministic executor reads the first HTTPS URL in the task text and labels the collected output, never fabricating a model recommendation.
14. Task preset is generic and capability-derived, not tied to a template name. Selecting a preset suggests tools/scopes/type; objective begins empty and is never silently overwritten by preset selection. Pointer selection has a quiet focus state; keyboard navigation retains a visible focus indicator.
15. Work details puts actual requested/granted values first, with identical black normal-weight values for granted items and gray only for requested-but-ungranted items. Unrequested capabilities are absent; pending and unknown issuance are not denials. Context uses historical caller/Agent/Policy/backend facts, never current setup. Activity is expandable without losing polling, keyboard controls or evidence links. Actual stored results are preserved and unnecessary explanatory copy removed.
16. The local deterministic Researcher chooses the tool needed by a supplied public HTTPS URL even when the effective catalog is empty or unrelated. It actually attempts the installed route through the Gateway; denial fails the task without a default model answer. Missing tool, missing scope and empty requested tools/scopes have real refusal facts and zero downstream attempts. Generic tool-free tasks remain valid. This is local agent behavior, not a new platform intent router or permission source.
17. Owner-approved failure-banner refinement: failed Work shows recorded refusals directly below the title, before Permissions, using a compact amber banner with only `<target> blocked` and an `Evidence` link. No arrows or explanatory subtext. Successful/running Work keeps its quiet refusal list after Permissions; no refusal fact means no blocked banner. The original authority snapshot and detailed failure/evidence remain unchanged. Local acceptance only; no merge/deployment.
